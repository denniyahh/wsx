<objective>
`peel_commit` refuses whatever is not a full object id of the repository's own hash kind, as git
does, and never crashes. Task 1 adds the hash-kind refusal behind a RED test, which today panics
inside gix-odb. Task 2 pins that a branch name, an abbreviated id, an empty id and a
describe-shaped ref name are refused at the id boundary while git would resolve them. That
contrast is D-01's point and the git-layer half of D-04.

Purpose: 03.1-01 left `to_gix` as hex decoding without the kind check (RESEARCH Pitfall 1),
and nothing yet shows that the id boundary refuses names. Phase 4's exact ref reads and every
Phase 5+ caller rely on both.
Output: `to_gix(&self, kind)`, seven `git::refs::tests::` tests.
</objective>

Otherwise it returns `Error::Gix { what: format!("read object id {self}"), message: format!("a {} id in a {kind} repository", id.kind()) }`. Research measured the rendering `read object id 2c86d84a…: a sha1 id in a sha256 repository`. Without the check, gix-odb's `debug_assert_eq!(self.object_hash, id.kind())` (`gix-odb-0.87.0/src/store_impls/loose/find.rs` line 12) panics in a test build. A release build reads the id as missing instead, so behaviour would differ between builds.
