# Phase 03.1: Resolve ref names as git does - Context

**Gathered:** 2026-11-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 3's `Repo` reads (`merge_base`, `ahead_behind`, `range_walk`, `tree_diff`) take revspec strings
and resolve them with gix's `rev_parse_single` (`Repo::resolve`, `Repo::resolve_commit` in
`src/git/repo.rs`). gix tries a name as a hex prefix and then as `describe` output before it tries
refs; git tries refs first. Measured on gix 0.90.0 and git 2.56.0: a ref named
`refs/remotes/origin/rel-1-g<7 hex>` (or its short form `origin/rel-1-g<7 hex>`), whose hex part
prefixes another existing object, resolves in gix to that other object, while
`git rev-parse --verify` and gix's exact `try_find_reference` give the ref's own commit. Control: with
hex that prefixes no object, all three agree. A wsx command that hands these reads a branch name can
therefore get a different commit than git, silently.

This phase removes revspec parsing from the git layer, so no wsx read can resolve a name differently
from git. It does not add name lookup: exact ref reads arrive with Phase 4 (`find_ref`,
`ref_commit`).

</domain>

<decisions>
## Implementation Decisions

### Read inputs
- **D-01:** `merge_base`, `ahead_behind`, `range_walk` and `tree_diff` take commit ids (the crate's
  `git::ObjectId`), never revspec strings. No production caller exists yet (checked: only tests in
  `src/git/reads.rs` and `src/git/repo.rs` call them, with `HEAD`), and every planned input is either
  an id from the repo model or a branch name (`wsx new|land|rm <branch>`), which is read by exact ref
  name, not parsed. — **Reversibility:** costly — every Phase 5+ caller is written against id inputs;
  going back to strings re-opens this defect class.
- **D-02:** `Repo::resolve` and `Repo::resolve_commit` are removed. An id becomes a commit through
  `pub fn peel_commit(&self, id: &ObjectId) -> Result<ObjectId, Error>` (peeling an annotated tag)
  and the private `fn peeled_commit(&self, id: &ObjectId)`, with exactly the signatures plan 04-01
  already specifies, so Phase 4 reuses them instead of defining a second peel. Converting an
  `ObjectId`'s hex to a gix id is hex decoding, not revspec parsing.

### Ban on revspec parsing
- **D-03:** gix's revspec parsing entry points are added to `clippy.toml`'s `disallowed-methods`
  with a reason naming this defect, in the same shape as the existing gix open/discover group: at
  least `gix::Repository::rev_parse` and `gix::Repository::rev_parse_single`; research lists every
  public revspec-parsing entry point of gix 0.90.0. The ban is pinned the way
  `banned_gix_entry_points_refuse_a_missing_path` pins the open group, so a misspelled or renamed
  path is caught, and a planted call in a scratch copy must fail `scripts/check.sh clippy` (negative
  control, as Phase 3 did for the open ban). Tests that need git's answer for a name ask the git CLI
  (the oracle), not gix.

### Names users pass (constraint for later phases, not built here)
- **D-04:** A user's `<branch>` argument is read as exactly `refs/heads/<branch>` (validated as a
  branch name), never through git's DWIM ladder or a revspec parser. A branch named like a hex
  prefix (`abc1234`) or like describe output (`rel-1-gdeadbee`) therefore reads that branch, as git
  does for an existing branch of that name.

### Claude's Discretion
The operator delegated all four gray areas (read inputs, branch-name lookup, hex-shaped names,
proof of parity) to Claude on 2026-11-03. D-01 to D-04 are Claude's choices. Planner discretion:
test-fixture shape for obtaining ids (e.g. `git rev-parse` in the fixture), and naming within the
existing conventions.

</decisions>
