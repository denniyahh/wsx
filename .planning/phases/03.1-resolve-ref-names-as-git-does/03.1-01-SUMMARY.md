# Phase 03.1 Plan 01: merge_base on object ids through peel_commit Summary

**`Repo::merge_base` now takes `git::ObjectId`s, decodes their hex with `gix::ObjectId::from_hex` and peels each through the new `Repo::peel_commit`, so a ref named `refs/remotes/origin/rel-1-g<hex>` gets git's merge-base (ONE) instead of the commit its hex prefixes (Y).**

## What this does not establish

- After GREEN, `merge_base_of_a_describe_shaped_ref_matches_git` cannot exercise name resolution any more, because `merge_base` no longer takes a name. It pins git parity for the ids git names. The lasting guards against a name reaching gix's parser are 03.1-02's name-refusal tests and 03.1-04's clippy ban.
- The tracer covers one read, on the defect fixture and the Phase 3 fixtures. At this plan's tip, `ahead_behind`, `range_walk` and `tree_diff` still take revspec bytes through `Repo::resolve` / `Repo::resolve_commit`. 03.1-03 moves them.
- `to_gix` does not yet check the hash kind. 03.1-02 adds that. Until then, an id of the other kind panics inside gix-odb in a test build and reads as missing in a release build (RESEARCH Pitfall 1). No caller passes one yet.
- `peel_commit` follows `refs/replace/` through gix's object lookup. The parity claims hold only for repositories without replace refs (RESEARCH Pitfall 9).
- The identity mutant shows that the tag tests reject an implementation that returns its input. No mutant was run that peels only one level. The nested test's `assert_ne!(peeled, inner)` and its equality with git cover that case by construction, but not by measurement.
