# Phase 03.1 Plan 02: Hash-kind refusal and name refusal at the id boundary Summary

**`ObjectId::to_gix` now takes the repository's `gix::hash::Kind` and refuses an id of the other kind as `read object id <hex>: a sha1 id in a sha256 repository` (and the reverse) before gix-odb's `debug_assert` can crash. Seven tests pin that refusal, and that a branch name, a 7-hex prefix, an empty id and a describe-shaped ref name never get through the id boundary, though git resolves them.**

## Accomplishments

- An id of the other hash kind was a crash in a test build. It is now a refusal naming both kinds, in both directions. git refuses the same input (non-zero exit).
- A SHA-256 annotated tag still peels to git's 64-character commit. This test is the control that the check accepts a matching kind.
- A branch name, an abbreviated id, an empty id and a full describe-shaped ref name are refused with gix's `A hash sized <n> hexadecimal characters is invalid`. For each of these except the empty id, the test shows git resolving the same input. This is D-01 and the git-layer half of D-04.

## What this does not establish

- The hash-kind tests cover a SHA-1 id in a SHA-256 repository and the reverse, with ids of real commits. They do not cover a hash kind gix might add later.
- The name tests show that `peel_commit` decodes hex only. They do not show how a later phase reads a user's branch name. That is D-04's constraint on Phases 4 and 8, which 03.1-04 records in STATE.md.
- The empty-id test pins the decode message for `""`. It does not catch a revspec fallback, because gix's parser refuses `""` too (measured with the mutant above). The branch, prefix and describe-shaped tests are what catch a fallback.
- Each mutant was run once, against the tests named above, not the whole suite.
- The release-build behaviour that the check prevents (an id of the other kind read as missing) was not measured here. That comes from RESEARCH Pitfall 1.
