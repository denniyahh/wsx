## Warnings

### WR-01: The four describe-shaped read tests cannot fail for the reason their names give

**File:** `src/git/reads.rs:448-477`, `src/git/reads.rs:649-675`, `src/git/reads.rs:681-711`, `src/git/reads.rs:795-822`
**Issue:** Each test gets its inputs through `id(&scratch, &fixture.repo, name)`, which is
`git rev-parse --verify` (`src/git/testing.rs:311-313`). The describe-shaped name is resolved
by git before wsx sees it, so the read only ever receives ONE's id. The tests then reduce to
existing equal-input cases:

| Describe-shaped test | Inputs it actually passes | Existing test it duplicates |
|---|---|---|
| `range_walk` | ONE --not ONE | `range_walk_with_every_tip_hidden_is_empty` (`:1031`) |
| `ahead_behind` | ONE vs ONE | `a_commit_with_itself_is_its_own_merge_base_and_level` (`:899`) |
| `tree_diff` | ONE vs ONE | `tree_diff_of_a_revision_with_itself_is_empty` (`:859`) |
| `merge_base` | ancestor ONE vs Y | the ancestor case near `:953` |

Their assertion messages say "gix's revspec parser reads {name} as {other}", but no gix
parser runs in them.

These tests were meaningful when written: they were the RED step against the old string
API, and commit 8fa320f called `merge_base(name.as_bytes(), b"other")`. Once GREEN changed
the signatures they became tautological. The defect is now held off by the `&ObjectId`
signatures and the clippy ban, and pinned by
`banned_gix_revspec_parsers_read_a_describe_shaped_ref_as_another_object`, not by these four
tests. Kept as they are, they report coverage that does not exist. That is the
"non-discriminating assertion" shape the project's test rules forbid.

**Fix:** Delete the four tests. If any is kept, rename it to the behaviour it actually tests
(for example `tree_diff_of_two_ids_of_one_commit_is_empty`) and drop the gix-parser wording
from its message. Put the defect's regression guard in one place: the existing pin test, plus
a doc line on each read saying that the `&ObjectId` signature is the guard.

### WR-02: `range_walk` with no tips accepts any hidden id, which git refuses

**File:** `src/git/reads.rs:83-94`
**Issue:** The new doc says the function "takes object ids, each peeled to its commit". But
`if tips.is_empty() { return Ok(BTreeSet::new()); }` returns before
`self.commit_ids(hidden)` runs. So `range_walk(&[], &[ObjectId("main"…)])`, an id of the
other hash kind, or a missing id all return `Ok(empty)`. git 2.56.0 refuses the same input:
`git rev-list --not 0123456789012345678901234567890123456789` exits 128 with
`fatal: bad object`, and a 64-hex id in a SHA-1 repository exits 128 too (verified during this
review). The early return predates this phase, but the new doc claims a validation that does
not happen on this path. A Phase 5 caller that builds `hidden` from a bad model value gets a
silent empty answer instead of an error, which conflicts with the project's fail-closed rule.
**Fix:** Validate before the early return:
```rust
let hidden_ids = self.commit_ids(hidden)?;
if tips.is_empty() {
    return Ok(BTreeSet::new());
}
let tip_ids = self.commit_ids(tips)?;
```
Add a test asserting that `range_walk(&[], &[foreign_id])` is `Err`, with git's refusal of
`rev-list --not <id>` as the oracle. Alternatively, keep the behaviour and make the doc say
that hidden ids are not read when there are no tips.

### WR-03: `tree_of`'s accept and refuse paths are untested at the id boundary

**File:** `src/git/reads.rs:156-173`
**Issue:** `tree_of` makes its own `to_gix(self.repo.object_hash())` call and its own
find/peel. Its doc promises four behaviours:

- A tree id is itself.
- An annotated tag peels to its tree.
- An id of the other hash kind is `to_gix`'s refusal.
- A missing or non-tree-ish object is `Error::Gix` naming the id.

No test in `src/git/reads.rs` calls `tree_diff` with a tree id, a tag id, a blob id, a missing
id or a wrong-kind id. `rg` finds no `tree of` or `read object id` assertion in that file;
every `tree_diff` test passes commit ids from `git rev-parse`. The `refs.rs` tests cover the
same shapes only for `peel_commit`, which `tree_diff` does not call. The SHA-1/SHA-256 check
that guards gix-odb's `debug_assert` in `tree_diff` is therefore unpinned. So is the claim
that it takes a tree-ish "as `git diff-tree` takes one".
**Fix:** Add tests in the style of the `refs.rs` peel tests, with `git diff-tree` as the
oracle:

- `tree_diff(&tree_id, &commit_id)` and `tree_diff(&tag_id, &commit_id)` equal git's output.
- `tree_diff(&blob_id, …)` and `tree_diff(&missing_id, …)` are `Error::Gix` rendering
  `tree of <hex>: …`.
- `tree_diff(&sha1_id, …)` in a SHA-256 repository renders
  `read object id <hex>: a sha1 id in a sha256 repository`.

### WR-04: A misspelled `DISCOVERING_SUITES` entry passes silently

**File:** `src/git/testing.rs:1054-1058`, `src/git/testing.rs:1098-1112`
**Issue:** This phase adds `"git::refs::tests::"` to the libtest filters re-run under a hook's
`GIT_DIR`/`GIT_INDEX_FILE`. The runner passes all three filters in one invocation (libtest
ORs them) and asserts only `passed > 0` and `failed == 0` over the combined count. If an
entry matches no test, because of a typo or because the module is renamed, its suite silently
stops being exercised under the hook environment while the check stays green. This is the
repo trap CLAUDE.md names ("A nextest filter that matches nothing must fail"), in libtest
form. Nothing ties the list to the set of modules that call `rerun_scrubbed()` either, so a
new discovering module that is left out gets no hook-environment run.
**Fix:** Run each filter in its own invocation and require `passed > 0` for each one:
```rust
for suite in DISCOVERING_SUITES {
    let output = Command::new(&exe).arg(suite) /* same env as today */ …;
    let stdout = String::from_utf8_lossy(&output.stdout);
    assert!(matches!(libtest_counts(&stdout), Some((passed, 0)) if passed > 0), "{suite} …");
}
```
Optionally, add a test
that greps `src/git/**/*.rs` for `rerun_scrubbed()` callers and asserts that each module
prefix is in `DISCOVERING_SUITES`.

### WR-05: The `mailmap` exclusion that keeps gix's internal revspec parse unreachable rests on a comment

**File:** `Cargo.toml:21-24`
**Issue:** The comment correctly records that gix's `open_mailmap_into` calls
`rev_parse_single` internally (`gix-0.90.0/src/repository/mailmap.rs:31`, verified), which
the clippy ban cannot see, because clippy checks wsx's call sites and not gix's. Nothing
mechanical keeps the feature off. Adding `"mailmap"` to the feature list, or adding any
dependency that enables `gix/mailmap` through feature unification, would reopen a revspec
path with no gate failing. The test pin covers the four public entry points, but not this
transitive one.
**Fix:** Enforce it in `deny.toml`, which `scripts/check.sh deps` already runs (cargo-deny
0.20.2 is pinned and supports per-crate feature bans; check the exact key names against that
version):
```toml
[[bans.features]]
crate = "gix"
deny = ["mailmap"]
```
Then prove the ban bites: in a scratch copy, add `mailmap` to the gix features and confirm
that `scripts/check.sh deps` fails.

## Info

### IN-01: `commit_id` round-trips through hex instead of using `peeled_commit`

**File:** `src/git/reads.rs:181-185`
**Issue:** `self.peel_commit(id)?.to_gix(self.repo.object_hash())` encodes the peeled
commit's gix id to a hex `String` and then decodes and kind-checks it again. D-02 made
`peeled_commit` private so that callers inside the git layer reuse it. The result is correct;
the extra conversion is redundant, and it adds a second error path that cannot be reached.
**Fix:** `self.peeled_commit(id).map(|commit| commit.id)`. This needs `peeled_commit` to be
`pub(super)`, or `commit_id` to move into `refs.rs`.

### IN-02: `to_gix` accepts uppercase hex, but `ObjectId` is documented as lowercase

**File:** `src/git/mod.rs:36-38`, `src/git/mod.rs:57-58`
**Issue:** `gix::ObjectId::from_hex` decodes with `faster_hex::hex_decode`, which accepts both
cases. An `ObjectId("ABC…")` built inside the git module would peel successfully, but it
compares unequal (derived `PartialEq` on `String`) to the lowercase `ObjectId` that
`from_gix` returns for the same object. Today only `from_gix` and test helpers that use git
output construct ids, so nothing reaches this. It is an unenforced invariant.
**Fix:** In `to_gix`, refuse any input that is not all lowercase hex
(`self.0.bytes().all(|b| matches!(b, b'0'..=b'9' | b'a'..=b'f'))`), or record in the doc
that the invariant holds only by construction.

### IN-03: Commit reads refuse non-commit tips or hidden ids, which git ignores

**File:** `src/git/reads.rs:93-94`, `src/git/refs.rs:18-28`
**Issue:** Verified on git 2.56.0: `git rev-list <tree-id>`, `git rev-list --not <tree-id>`
and `git rev-list HEAD --not <tree-id>` all exit 0, because without `--objects` git drops
non-commit objects from the walk. `range_walk` and `ahead_behind` return `Error::Gix` for the
same input. This predates the phase (the removed `resolve_commit` behaved the same), and it
fails closed, so it is a documented divergence rather than a wrong answer.
**Fix:** Add a sentence to `range_walk`'s doc stating that a non-commit id is refused where
git ignores it.

### IN-04: Stale "revision" naming on helpers that now carry object ids

**File:** `src/git/repo.rs:2973-3016`, `src/git/reads.rs:859`
**Issue:** `REV_VAR`, `ObjectRun`'s doc ("one revision"), `object_run`'s `rev` parameter and
`git cat-file -t <rev>`, and the test name `tree_diff_of_a_revision_with_itself_is_empty` all
still say "revision" after this phase changed them to carry hex ids. They are only
misleading for a reader, since the code is correct.
**Fix:** Rename to `ID_VAR`/`id`, and to `tree_diff_of_a_commit_with_itself_is_empty`.
