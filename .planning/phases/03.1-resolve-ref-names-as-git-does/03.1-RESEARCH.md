- **D-02:** `Repo::resolve` and `Repo::resolve_commit` are removed. An id becomes a commit through

  already specifies, so Phase 4 reuses them instead of defining a second peel. Converting an
  `ObjectId`'s hex to a gix id is hex decoding, not revspec parsing.

#### Ban on revspec parsing
- **D-03:** gix's revspec parsing entry points are added to `clippy.toml`'s `disallowed-methods`
  with a reason naming this defect, in the same shape as the existing gix open/discover group: at
  least `gix::Repository::rev_parse` and `gix::Repository::rev_parse_single`; research lists every

## Summary

The defect is real at the read level on the current code, measured this session on gix 0.90.0 and git 2.56.0. In a repo where `refs/remotes/origin/rel-1-g1f12ccf` holds commit ONE (`f25bcc35…`) and `1f12ccf…` is commit Y (a child of ONE), the current `Repo::merge_base(b"refs/remotes/origin/rel-1-g1f12ccf", b"other")` returns Y, while `git merge-base` returns ONE. `range_walk(&[name], &[b"main"])` returns 1 commit where `git rev-list --count` returns 0. The cause is in the parser itself, not in gix's resolver: `gix_revision::spec::parse` tries the hex prefix (`try_set_prefix`) and then describe output before `delegate.find_ref` (`gix-revision-0.52.0/src/spec/parse/function.rs:472-488`). A recording delegate showed the call order `["disambiguate_prefix", "find_ref"]` for the describe-shaped name and `["find_ref"]` for `refs/heads/main`.

gix 0.90.0 (with this crate's `sha1, sha256, revision` features) has exactly four public revspec-parsing entry points: `gix::Repository::rev_parse`, `gix::Repository::rev_parse_single`, `gix::revision::Spec::from_bstr` and `gix::revision::plumbing::spec::parse`, the last being the re-exported `gix_revision::spec::parse`. One more internal caller, `Repository::open_mailmap_into`, is compiled out because the `mailmap` feature is off. clippy 0.1.99 resolves all four paths. With all four in `clippy.toml` and each called once under its own `#[expect(clippy::disallowed_methods)]`, clippy exits 0. Misspelling any one of the four printed `does not refer to a reachable function` (a warning only) plus `this lint expectation is unfulfilled` (an error, rc 101) at that call's expect. A call planted in a scratch copy failed `scripts/check.sh clippy` with rc 101 and `use of a disallowed method`. The same copy without the planted call passed with rc 0.

Peeling an id needs no parsing: `gix::ObjectId::from_hex` decodes exactly 40 or 64 hex characters and refuses everything else (`gix-hash-0.28.1/src/object_id.rs:64-96`). One hazard was found. Given an id of the other hash kind, `find_object` panicked in the test build (gix-odb `debug_assert_eq!(self.object_hash, id.kind())`), where git refuses with exit 128. `peel_commit` must therefore compare `id.kind()` with `repo.object_hash()` before any lookup. A prototype of the whole phase passed fmt, clippy `-D warnings` and all 116 unit tests in a scratch copy. That covered `peel_commit`/`peeled_commit` in a new `src/git/refs.rs`, `ObjectId::to_gix` in `src/git/mod.rs`, the four reads on `&ObjectId`, the ban and pin, and the converted tests. The suite turned up one caller that grepping for method names had missed: `object_run(..., "HEAD", ...)` passes a name to the test child through an environment variable.

**Primary recommendation:** Put `peel_commit` and the private `peeled_commit` in a new `src/git/refs.rs`, where 04-01 already puts them. Put the single hex-to-gix conversion, with the hash-kind check, next to `ObjectId::from_gix` as `ObjectId::to_gix`. Switch the four reads to `&ObjectId` / `&[ObjectId]`. Ban the four entry points in one `clippy.toml` group. Pin them with a test that calls each one under its own `expect` and asserts that the defect still reproduces.

### Pattern 1: Hex decode with a hash-kind check (the only hex-to-gix conversion)
**What:** `ObjectId::to_gix(&self, kind)`: `from_hex`, then compare `id.kind()` with the repository's `object_hash()`.
**Why:** `from_hex` accepts exactly 40 hex characters (SHA-1) or 64 (SHA-256) and refuses everything else. Measured: a 7-character prefix gave `A hash sized 7 hexadecimal characters is invalid`, `main` gave `A hash sized 4 …`, the empty string `… 0 …`, 41 characters `… 41 …`, 40 non-hex characters `Invalid character encountered`. Uppercase decoded fine. [VERIFIED: probe run, gix-hash-0.28.1/src/object_id.rs:64-96, quoted: `pub fn from_hex(buffer: &[u8]) -> Result<ObjectId> {` … `len => Err(message!("A hash sized {len} hexadecimal characters is invalid").validation_error()),`]. A SHA-1 id looked up in a SHA-256 repository panicked in the test build, and so did the reverse (`assertion left == right failed, left: Sha256`), at `gix-odb-0.87.0/src/store_impls/loose/find.rs:12`, quoted `debug_assert_eq!(self.object_hash, id.kind());` [VERIFIED: probe run + Read]. git refuses the same input: `git rev-parse --verify <40-hex>^{commit}` in a SHA-256 repo printed `fatal: Needed a single revision`, rc 128 [VERIFIED: measured].
**Example (compiled, clippy-clean and exercised in the prototype):**
```rust
// src/git/mod.rs, in `impl ObjectId`, beside `from_gix`
/// The gix form of this id in a repository whose objects are hashed
/// with `kind`: hex decoding only, never revspec parsing, so no ref is
/// read and no prefix or describe output is expanded. An id of another
/// hash kind is refused here, as git refuses it; gix-odb would
/// `debug_assert` on it.
fn to_gix(&self, kind: gix::hash::Kind) -> Result<gix::ObjectId, Error> {
    let failed = |message: String| Error::Gix {
        what: format!("read object id {self}"),
        message,
    };
    let id =
        gix::ObjectId::from_hex(self.0.as_bytes()).map_err(|err| failed(err.to_string()))?;
    if id.kind() == kind {
        Ok(id)
    } else {
        Err(failed(format!("a {} id in a {kind} repository", id.kind())))
    }
}
```
Measured message for the mismatch: `read object id 2c86d84a…: a sha1 id in a sha256 repository`.

### Pattern 2: `peel_commit` / `peeled_commit` with 04-01's exact signatures
**What:** These are 04-01's contract signatures [VERIFIED: .planning/phases/04-repo-model/04-01-PLAN.md:111, quoted: "`pub fn peel_commit(&self, id: &ObjectId) -> Result<ObjectId, Error>` (the commit `id` names, peeling an annotated tag: the private `fn peeled_commit(&self, id: &ObjectId) -> Result<gix::Commit<'_>, Error>` does `gix::ObjectId::from_hex` on the id's hex, then `find_object` and `peel_to_commit`, the body of `resolve_commit` without its revspec step, so no ref is read, and `peel_commit` returns that commit's id as wsx's `ObjectId`)"]. 04-01's error shape is `Error::Gix { what: "peel <hex> to a commit", message }` [VERIFIED: 04-01-PLAN.md:184].
**Where:** `src/git/refs.rs`, a new file. `peeled_commit` is private (D-02), so it can only be called from inside the `refs` module. 04-01's `root_entry` lives in `refs.rs` and calls it [VERIFIED: 04-01-PLAN.md:68-72]. Putting the two functions in `repo.rs` or `reads.rs` would force 04-01 to widen `peeled_commit` to `pub(super)`, which contradicts D-02. 04-07's key link also names `src/git/refs.rs peel_commit` [VERIFIED: 04-07-PLAN.md:49].
**Example (compiled, clippy-clean, the tests below passed):**
```rust
//! Peeling an object id to the commit git names for it.

use super::repo::Repo;
use super::{Error, ObjectId};

impl Repo {
    /// The commit `id` names, peeling annotated tags as git's
    /// `<id>^{commit}` does. No ref is read and no revspec is parsed.
    pub fn peel_commit(&self, id: &ObjectId) -> Result<ObjectId, Error> {
        self.peeled_commit(id)
            .map(|commit| ObjectId::from_gix(&commit.id))
    }

    /// The commit `id` peels to, as gix's commit.
    fn peeled_commit(&self, id: &ObjectId) -> Result<gix::Commit<'_>, Error> {
        let gix_id = id.to_gix(self.repo.object_hash())?;
        self.repo
            .find_object(gix_id)
            .map_err(|err| err.to_string())
            .and_then(|object| object.peel_to_commit().map_err(|err| err.to_string()))
            .map_err(|message| Error::Gix {
                what: format!("peel {id} to a commit"),
                message,
            })
    }
}
```

**Pin test** (prototype, passed, in `repo.rs`'s test module beside the open-group pin): a recording delegate `Lookups(Vec<&'static str>)` implements `Revision` (5 methods), `Navigate` (4), `Kind` (1) and `Delegate::done`. Every lookup records its name and returns `Err(gix::error::message("refused").validation_error())`. The test:
1. builds `main` = ONE, `other` = Y (child), and `git update-ref refs/remotes/origin/rel-1-g<Y[..7]> <ONE>`
2. asserts git's oracle `git rev-parse --verify <name>` == ONE
3. calls each of the four entry points once, each `let` under its own `#[expect(clippy::disallowed_methods, reason = "pins clippy.toml's revspec ban: …")]`
4. asserts `rev_parse_single`, `rev_parse(..).single()` and `Spec::from_bstr(.., Default::default()).single()` each give Y, and that the plumbing parse is `Err` with `lookups.0 == ["disambiguate_prefix", "find_ref"]`.

Negative control, measured: with the name `refs/remotes/origin/rel-1-gdeadbee`, the test failed (`rev_parse_single … left: Some(<ONE>) right: Some(<Y>)`). Its assertions therefore depend on the hex prefixing Y, not on a constant.

### Anti-Patterns to Avoid
- **One `#[expect]` on the whole pin test:** it stays fulfilled while a misspelled path leaves one call unchecked. Phase 3 measured this [CITED: 03-RESEARCH.md:444]. Put one `expect` on each `let`.
- **Banning before `resolve` is gone:** with the four entries in place and `resolve` still present, clippy failed with rc 101 at `src/git/repo.rs:163:25` (`use of a disallowed method gix::Repository::rev_parse_single`) [VERIFIED: measured]. Land the ban in the commit that removes `resolve`, or after it.
- **A `pub(super)` `peeled_commit` to let `reads.rs` reach it:** this contradicts D-02's "private". `reads.rs` goes through `peel_commit` and decodes again (`commit_id`), at negligible cost.
- **Getting test ids from gix (`rev_parse_single`) instead of git:** D-03 forbids it, and the ban makes it a clippy error.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Hex to object id | a hex parser, or `rev_parse_single(hex)` | `gix::ObjectId::from_hex` | exact-length and charset checks are built in. `rev_parse` adds the prefix and describe semantics this phase removes |
| Peel tag to commit | a hand loop over `object.kind` | `gix::Object::peel_to_commit` | handles nested tags (measured `v1nest` → commit) |
| Ban enforcement | a grep in a script | clippy `disallowed-methods` + per-call `expect` pin | clippy resolves the path (re-exports included), and the pin catches renames and misspellings |
| Name to id in tests | gix resolution | `git rev-parse --verify <name>` via `testing::git_ok` | D-03 |

**Key insight:** gix's revspec order is a property of the parser (`gix_revision::spec::parse`), not of a resolver wsx could replace. Any revspec string handed to gix inherits it. Only id inputs remove the defect class.

## Common Pitfalls

### Pitfall 1: A SHA-1 id in a SHA-256 repo (or the reverse) panics in gix
**What goes wrong:** `find_object` hits `debug_assert_eq!(self.object_hash, id.kind())` and the test binary panics. In release it would only report "not found", so behaviour differs between builds.
**How to avoid:** do the kind check in `to_gix` (Pattern 1), before any lookup.
**Warning signs:** `assertion left == right failed … left: Sha256` from `gix-odb … loose/find.rs:12`.

### Pitfall 2: A stale ban path only warns
**What goes wrong:** `` `gix::…_misspelled` does not refer to a reachable function `` is a warning, and `-D warnings` does not turn it into an error. In run A, the bin target finished with "generated 1 warning" and the failure came only from the test target's expectation.
**How to avoid:** the per-call `expect` pin (Pattern 4). Measured for all four paths: each misspelling gave rc 101 with exactly one `this lint expectation is unfulfilled`, at that call's line.

### Pitfall 3: Orphans after removing `resolve`
**What goes wrong:** `Repo::unsupported_backend` (`repo.rs:193`) has no caller once `resolve` goes. Under the test cfg every item must be used, so clippy fails on dead code [CITED: 04-RESEARCH.md Pitfall 11]. The five tests that call `resolve` or name-based `tree_diff` go too, and with them the only caller of `open_unchecked` (`repo.rs:828`). Those tests are `reftable_ref_decode_maps_to_the_refusal`, `files_repo_resolves_head_through_the_same_path`, `tree_diff_keeps_the_reftable_refusal`, `files_repo_diffs_head_through_the_same_path` and `unknown_revision_is_not_reported_as_reftable`.
**How to avoid:** delete `unsupported_backend`, those five tests and `open_unchecked`. `twins`, `ref_storage` and `Error::Reftable` stay, used by `refuse_ref_storage` and its tests (`reftable_repo_is_refused`, `empty_reftable_repo_is_refused`, `files_backend_twin_opens`). Prototype: clippy clean after exactly these deletions. Note: this retires a Phase 3 locked behaviour; see Open Question 1.

### Pitfall 4: Callers that pass a name indirectly
**What goes wrong:** a grep for `resolve(`/`merge_base(` does not find `object_run(&scratch, &repo, "HEAD", …)`, which hands `HEAD` to the child through `WSX_TEST_REV`. In the prototype, `git::repo::tests::the_repository_object_store_reads_like_git` failed (and so did `git::testing::discovering_tests_pass_with_a_runner_git_dir`, which re-runs it) until `"HEAD"` became `&head`.
**How to avoid:** run the full suite. `git_object_directory_is_refused` also passes `"HEAD"`, but it passes anyway because discover refuses first. Convert it for consistency: `git cat-file -t <hex>` with an empty `GIT_OBJECT_DIRECTORY` still fails, which keeps the test's `assert_ne!(run.git.status.code(), Some(0))`. That last point is [ASSUMED], see A2.

### Pitfall 5: git's oracle exit codes and existence checks
**What goes wrong:** `git rev-parse --verify <full-hex>` without a peel suffix succeeds for an object that does not exist: it printed the hex. `--verify -q` exits 1, while plain `--verify` exits 128 [VERIFIED: measured both].
**How to avoid:** use `git rev-parse --verify <hex>^{commit}` as the oracle for `peel_commit`, and assert a non-zero exit, or the exact code for the flag used.

### Pitfall 6: Names and short hex are refused, though git accepts them
`peel_commit(&ObjectId("main"))` and a 7-character prefix are `Err` (`read object id …: A hash sized N hexadecimal characters is invalid`), while `git rev-parse --verify main^{commit}` and `<7 hex>^{commit}` succeed. This is the point of D-01, not a parity failure. Tests must not assert "matches git" for these inputs. Assert the refusal, with git's success as the documented contrast.

### Pitfall 7: `tree_diff` peels a tree-ish, the commit reads peel to a commit
git measured on the same fixture: `git diff-tree <tag> ONE` and `git diff-tree <tree> ONE` exit 0; `<blob>` gives `fatal: unable to read tree`, rc 128; a missing object gives `fatal: bad object`, rc 128. `git merge-base <tree|blob> ONE` gives `error: object … is a tree, not a commit`, rc 128. `git rev-list <tree|blob>` prints nothing and exits 0, where wsx's `range_walk` refuses. That divergence already exists (today's `resolve_commit` refuses too), it is fail-closed, and it is outside D-01's commit-id inputs. Recommendation: keep `tree_of`'s `peel_to_tree` (tree-ish, like `git diff-tree`) and keep `commit_id` for the three commit reads.

### Pitfall 8: RED evidence for a signature change
**What goes wrong:** a test written against `&ObjectId` before the change fails to compile, which is nextest status 101, not a test failure, so it is not valid RED evidence.
**How to avoid:** use one of two RED shapes, both measured. (a) A read-level test against the current string API on the defect fixture: current `merge_base(name, b"other")` = Y (`1f12ccf…`) while `git merge-base name other` = ONE (`f25bcc3…`); current `range_walk(&[name], &[b"main"])` has 1 commit while `git rev-list --count name --not main` = 0. (b) 04-01's stub pattern: the new signatures with wrong bodies, so assertions fail.

### Pitfall 9: replace refs are not covered
`peel_commit` uses gix's object lookup, which follows `refs/replace/`. Phase 4's 04-11 measures one replacement reading alike and refuses chains, but only inside `root_entry` [CITED: 04-11-PLAN.md:22, 180]. This phase's parity claims hold for repositories without replace refs. State that limit in the SUMMARY.
