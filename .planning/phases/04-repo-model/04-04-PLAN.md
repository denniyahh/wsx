`Problem` variants this plan adds, each with a `///` line and a `Display` arm:
- `LineEndsInCr`: `the line ends in a carriage return (CRLF line endings are not allowed)`
- `EmptyPath`: `the path is empty`
- `AbsolutePath`: `the path starts with /`
- `EmptyComponent`: `the path has an empty component (//)`
- `DotComponent`: `the path has a . or .. component`
- `Nul`: `the path contains a NUL byte`
- `Overlap { other_line: usize, other_text: Vec<u8> }`: `this line overlaps line {other_line}: {other_text}; a path cannot be both only and modified` with `other_text` through `c_quote`

`pub fn normalize_path(path: &[u8]) -> Result<Vec<u8>, Problem>` per RESEARCH lines 495-508. NUL is not in D-14's list, but D-14's reason covers it (it could never match a git tree path), so it is applied without a new decision (RESEARCH Pitfall 6). The check order in `parse`, so each row of RESEARCH's table gets its stated result: a line ending in CR first (a comment too), then comment and empty, then keyword, then the value's quoting, then `normalize_path`, then the overlap check against earlier entries. That order makes `LineEndsInCr` the result for a bare path ending in CR, which D-19 states as its own rule; `only a`, CR, `/` does not end in CR, so 04-03's test for it stays `EdgeWhitespace`. `normalize_path` takes over the one-`/` strip: Task 1's GREEN step removes it from `parse`, whose edge-whitespace check still looks past one trailing `/` but passes the value on whole, so `only a//` reaches `normalize_path` as `a//` and is `EmptyComponent` rather than stripped twice.

A line equal to exactly `only` or `modified` is `EmptyPath`; a line that starts with the keyword followed by anything other than one space is `UnknownKind`.

A deliberate difference from the oracle: `read -r KIND ENTRY _` reads `only a b` as `a` and `only<tab>a` as `a`. D-19 reads the first as `a b` and refuses the second. `.workspace-divergence` in this repository has neither shape. A test must copy its real shape inline: never `include_bytes!` it, because that file does not exist on the PR branches this code lands on.
