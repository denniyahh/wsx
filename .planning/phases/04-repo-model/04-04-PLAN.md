The size limit (third review, finding 8; operator ruling of 2026-11-05 under D-12, recorded in CONTEXT: "only ambiguity is invalid" contrasts ambiguity with staleness and does not forbid an explicit size limit; a manifest over 64 KiB is invalid). It is checked in `parse`, first, before any line is split or read: a manifest longer than `MAX_MANIFEST_BYTES` is `Err(ParseError { line, text: Vec::new(), problem: Problem::TooLarge { size } })`, where `line` is the 1-based number of the line holding byte index 65536 (its 65,537th byte), counting every line as `parse` does, so the owner sees where to cut. `text` stays empty, because the line holding that byte can be arbitrarily long and the error must not print it, and `ParseError`'s `Display` leaves out `: {text}` when `text` is empty, which only `TooLarge` produces (every other problem names a non-empty line; an empty line is skipped). It reaches the user through `model::Error::ManifestInvalid`, as every `ParseError` does, so it needs no new `model::Error` variant and no exit-code obligation of its own (phase 5's `ManifestInvalid` code covers it; 04-10's existing line "assign IF-01 exit codes to every model::Error variant" names it).

Why `parse` and not the blob read: checked first in `parse`, the limit stops all per-line work and the quadratic overlap check, which is the measured cost. It does not stop the whole-blob read, which happens in `root_entry` before `parse` runs; that read is linear in the blob's size, as `git cat-file blob` is.
