<objective>
Make the runner enforce the rules success criterion 4 sets: explicit expectations only, the
`fixed:` and `regression:` difference classes, known-positive and clean controls on every guard
scenario, at least one control on every HARN-06 case, and oracle sides that match how the
scenario is registered. Then make the disabled Rust sides visible by name in every full run.

Purpose: these rules are what turn a pile of scenarios into evidence. Without them a scenario can
pass by agreeing with the oracle, a `fixed:` claim can lack the oracle run that proves the defect,
and a guard can be observed only ever passing.
Output: the rule set in `scenario.rs` with one test per rejection, the control-running runner,
`registry.rs` with the report and the well-formed meta-test, and the nextest override.
</objective>

Encoding chosen here (discretion, recorded for later plans):
- `Class::{Parity, Fixed { defect: &'static str }, Regression { reason: &'static str }}`, set with `.class(...)` on a `Case`; default Parity.
- `OracleSide::{SameAsExpected, Recorded(Outcome), NotImplemented { why: &'static str }}`, set with `.oracle(...)`; default SameAsExpected.
- `Role::{KnownPositive, Clean, Counterpart}`; `Scenario::control(role, case)` adds a control case; each case carries its own config, fixture, action, expected outcome, class and oracle side.
- `CaseKind::{Merges, SquashMerged, ForkLayout, ScopedAndUnscoped, NoGsd, PathNames, ExistingPrBranch}`; `Scenario::harn06(kind)`.
- `Kind::{Oracle, RustOnly}` on `Entry`; new macro arm `name: rust_only, rust = "<reason>";` generates only the ignored `rust()` test.
- `is_guard(&Action)` is true for `Check` and `PrePush`.
- Parity rule for later plans: when the oracle and the intended wsx behaviour agree on the safety outcome (refuse or proceed, refs, commits, files), the case is Parity and its expected outcome is the oracle's observed one, exit code included; the phase that enables the Rust side revises the exit code if IF-01 defines another.
