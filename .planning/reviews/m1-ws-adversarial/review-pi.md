## CONFIRMED

**1. The pre-push guard is blind to merge commits, which is exactly where personal files enter a shared branch.**
`oracle-devflow/pre-push:91` and `:105` build the range with `git log --name-only --format=''`, and the comment at `:71` asserts "it lists every path touched by every commit in the range, add/modify/delete/rename all included". `REQUIREMENTS.md:81` (GUARD-01) inherits that claim verbatim: "checks every commit's touched paths in the range: add, modify, delete and rename into a personal path". Verified in a scratch repo: a merge whose conflict was resolved by adding `.planning/x.md` produces **no paths at all** for that merge under `git log --name-only`; only `-m` shows `.planning/x.md`. Git does not print a diff for a merge commit by default. `REQUIREMENTS.md:60-61` records that devflow's `develop-merge-or-squash` ruleset is "strict up-to-date", so merging the base into the PR/phase branch is the *mandated* workflow, not an exotic case — and that merge is the one commit the guard cannot see. A personal file added only during conflict resolution (agent writes `STATE.md` while resolving) is pushed.
*Fix:* GUARD-01 must specify `--diff-merges=first-parent` (or `-m`) plus `-z`, with a scenario "merge base into phase branch, resolve conflict by adding `.planning/STATE.md`, push must refuse" and a clean negative control.

**2. The cut silently drops code, and PRCUT-05's fidelity check cannot detect it by construction.**
`REQUIREMENTS.md:63` selects phase commits by conventional-commit scope only. `REQUIREMENTS.md:68` (PRCUT-05) fails only on "changes a path no replayed commit touched"; the oracle implements exactly that one-way comparison at `scripts/workspace/cut-pr-branch.sh:269` (`comm -13 TOUCHED_SET CHANGED_SET` = changed-but-not-touched). Nothing compares the *source* branch's code paths against what the PR ended up with. So an unscoped code commit (`fix: typo`, an agent commit without `(48)`, a commit whose scope is `(48.1)` while you cut `--phase 48`), a commit dropped because `git log --name-only` quoted the path, or a cherry-pick that replayed empty, disappears with a green run. That is precisely the failure `PROJECT.md:29-31` calls unacceptable, and PRCUT-05 has no negative control, so a mutant that removes the dropped-commit concept survives `cargo mutants`.
*Fix:* add a requirement: every commit in the source range that touches a non-personal path and is not replayed must have its patch-id present on the base (squash-landed) or the cut fails, naming it. Scenario: phase branch with one scoped and one unscoped code commit touching the same directory.

**3. The vendored oracle cannot run as vendored, and HARN-01's layout contradicts the personal-path policy.**
`REQUIREMENTS.md:29` (HARN-01) vendors the oracle "under `scripts/workspace/`", but the milestone's oracle set (`REQUIREMENTS.md:16-18`) includes `check-workspace-divergence.sh` and `pre-push`, which in this tree live in `oracle-devflow/`. Worse, `oracle-devflow/check-workspace-divergence.sh:30` reads its built-in list out of `scripts/cut-pr-branch.sh` — the port is at `scripts/workspace/cut-pr-branch.sh` — so the script exits 1 with its own "could not read FORBIDDEN_PATHS" message (`:32`) before checking anything, and `oracle-devflow/pre-push:209` calls `./scripts/check-workspace-divergence.sh`, which does not exist here. Separately, `.workspace-divergence` declares `only scripts/workspace`, so the oracle tree can never exist on `develop`, while REL-03 (`:123`) puts the gates on CI: the parity suite cannot run where the gates run.
*Fix:* HARN-01 must name the exact vendored layout and every path the oracle hard-codes, add an `oracle-selftest` scenario per script (run unmodified against a fixture, assert its own exit codes), and state which branch/job executes the parity suite and how the oracle reaches it.

**4. `oracle-devflow/` is itself an undeclared personal path — the leak is live in this snapshot.**
`.workspace-divergence` contains exactly two declarations (`only scripts/workspace`, `modified .gitignore`). The repo root carries `oracle-devflow/` (pre-push with the release-key fingerprint policy, pre-commit, check-workspace-divergence.sh, lint-phase-worktree.sh). It is not under a built-in (`REQUIREMENTS.md:40`, CONF-02), not `only`, and the current cut list (`scripts/workspace/cut-pr-branch.sh:120`) does not contain it. So on this branch today `wsx check` fails DIV-01 (`:74`), and `wsx cut` replays `oracle-devflow/*` onto the PR branch — devflow's personal hook policy, including the release-key and forbidden-pattern logic, in a public PR. The requirement set has no case for "a new top-level directory appears": no requirement forces classification of unlisted paths, and no scenario asserts what happens to a personal file in an unlisted directory.
*Fix:* put the oracle inside a built-in path; add a DIV requirement that every new top-level entry is either built-in, `only`, or a failure; add a cut scenario "personal file in an unlisted directory" with a negative control.

**5. The single resolved path list cannot express "this repo's `CLAUDE.md` is shared", and built-ins silently override declarations.**
The three lists really do disagree — `cut-pr-branch.sh:120` has `.cursor`, `AGENTS.md`, `graphify-out`, `.workspace-divergence`, bare `skills`; `pre-push:115` and `pre-commit:70` have `CLAUDE.md` and `.devflow` instead; `pre-commit:56-62` deliberately omits `.planning`. `WORKSPACE-MODE.md:68-69` additionally lists `scratch` as a real personal path in gsd-core and gsd-pi, in none of the lists. CONF-02 (`:40`) collapses this into one list that "the manifest extends". `CLAUDE.md` is the collision: wsx's own `develop` tracks it (it is in this checkout), devflow's `develop` tracks it (`DEVFLOW-SETUP.md:90`, "deliberately minimal (34 lines, public-safe)"). Including it in the single list means every PR that edits `CLAUDE.md` is dropped whole under PRCUT-02 (`:65`) or has the `CLAUDE.md` hunk stripped, and GUARD-01 refuses the push; excluding it drops the protection devflow has today. Neither `only` nor `modified` can subtract a built-in: `oracle-devflow/check-workspace-divergence.sh:69` skips built-ins *before* consulting ONLY/MODIFIED, so `modified CLAUDE.md` is accepted, never evaluated, and DIV-02 (`:75`) can never report it stale.
*Fix:* built-ins are defaults; add `shared <path>` to un-declare one per repo. DIV-02 must reject any declaration already covered by a built-in. Scenarios: a PR touching `CLAUDE.md` in wsx (kept) and in devflow (refused by policy) — the two answers must be recorded, not inferred.

**6. "Branches created by `wsx new`" and "PR branches cut by wsx" have no mechanism, so GUARD-04, WTREE-05 and STAT-01 are unfalsifiable and leak.**
`REQUIREMENTS.md:84` (GUARD-04) refuses personal paths "on PR branches cut by wsx" and allows them "on branches created from it by `wsx new`"; `:58` (WTREE-05) keys on "cut to a PR branch"; `:112` (STAT-01) reports "whether it has been cut". No requirement records a cut or a `new`. The only available discriminators are names, and every name is user-controlled: the template (`:44`), `workspace/<name>` (`:57`), and the cut's own `-pr` suffix (`cut-pr-branch.sh:76-88`). `feature/phase-48` and `feature/phase-48-pr` are indistinguishable by prefix, so any name heuristic admits `.planning` commits on the PR branch — exactly the branch that gets pushed — and GUARD-04's stated guarantee is false. WTREE-05 and STAT-01 cannot be asserted in a scenario at all.
*Fix:* a persisted mark written by `cut` and by `new` (e.g. `refs/wsx/cuts/<branch>`), read by GUARD-04, WTREE-05 and `status`; scenario: cut, commit `.planning/STATE.md` on the PR branch, commit must refuse; negative control on the phase branch must pass.

**7. MIG-03 contradicts REL-01, and removing the manifest blinds the oracle that is still installed.**
`REQUIREMENTS.md:108` (MIG-03) requires "Migration of the owner's real repos is verified on real state: devflow, gsd-core, gsd-pi"; `:121` (REL-01) says `.wsx.conf` is "migrated (MIG-01) at that point and not before". MIG-01 (`:106`) deletes `.workspace-divergence`. The still-installed oracle depends on that file twice: `cut-pr-branch.sh:121` reads `git show "$CURRENT_BRANCH:.workspace-divergence"` for the `only` entries (here, `only scripts/workspace` is the *only* thing keeping the workspace tooling out of PRs — it is not a built-in), and `pre-push:208` runs the divergence check only `if [ -f .workspace-divergence ]`. Migrating early — which MIG-03 practically requires — makes the oracle's cut replay `scripts/workspace/*` into PRs, and turns the divergence check into a silent skip, the fail-open shape both documents say is forbidden. Related hole: PRCUT-02 (`:65`) never says which revision of `.wsx.conf` is authoritative; the oracle deliberately reads the source branch's committed copy, but a phase worktree's working tree can hold a stale list after the workspace branch's manifest changes, so the cut strips the old list and the new personal path goes through.
*Fix:* make retirement atomic — `migrate` refuses while the oracle scripts are present, or keeps `.workspace-divergence` until REL-02; add `wsx migrate --verify` against a copy of real state; state in PRCUT-02 that the path list comes from the workspace branch tip, never the working tree.

**8. Squash-merged PRs break the ancestry assumptions of WTREE-05 and PRCUT-01, and no requirement mentions squash.**
`DEVFLOW-SETUP.md:60-61`: `develop-merge-or-squash` and `main-squash-only`; `oracle-devflow/CONTRIBUTING-workflow-b.md:37-39` tells you to merge the feature branch into the workspace branch and then sync. After a squash merge the phase's commits are ancestors of nothing: WTREE-05 (`:58`) refuses to remove the branch forever because it proves "merged" and "cut" by ancestry, so `--force` becomes routine and the guard stops guarding. Re-cutting the same phase (`PRCUT-01:63` selects `BASE_REF..branch`, and the base no longer contains those commits) replays commits whose content is already on the base: if identical they replay empty and are counted as excluded; if the squash carried review edits, the replay is a code conflict, which PRCUT-03/07 (`:66`, `:70`) turn into a permanent refusal with no diagnosis. The next sync then merges a base carrying the same hunks under different commits.
*Fix:* define "landed" as patch-id presence on the integration branch (no network needed), use it in WTREE-05 and `status`, and add scenarios: squash-merge → `wsx rm` succeeds; squash-with-edits → re-cut explains rather than conflicts.

**9. Pinning signing makes HARN-03's recorded "commit list" unreproducible, and PRCUT-02 asks for signing the oracle does not do.**
`REQUIREMENTS.md:30` (HARN-02) pins signing locally; `:31` (HARN-03) records expected "commit list" per scenario and the preamble promises "the same exit codes, refs, commits and trees"; `:65` (PRCUT-02) requires replayed commits "signed per the user's git config". devflow's tracked `.gitconfig` enables SSH signing for commits (`DEVFLOW-SETUP.md:54`), and an OpenSSH signature embeds a timestamp: two runs of the *oracle* produce different SHAs, so no hash can be recorded, and if the harness records subjects instead it no longer detects committer identity, date or signature regressions. The oracle also does not sign: `cut-pr-branch.sh:245` is `git commit -C "$HASH" --no-verify`, and `git cherry-pick` never signs — so PRCUT-02 silently smuggles in a behaviour change with no `fixed:` scenario, contrary to the preamble's rule that every intended difference is enumerated.
*Fix:* define parity over `subject | author | author-date | tree`, assert signature presence separately, and either enumerate the signing difference as a `fixed:` scenario or state that cut commits are unsigned.

**10. PRCUT-03's "no half-made PR branch" holds only on the predicted path, and a re-cut silently destroys an existing PR branch.**
`REQUIREMENTS.md:66` (PRCUT-03) promises "no half-made PR branch"; `:70` (PRCUT-07) admits cherry-pick failures that were *not* predicted and only requires "aborts with git's error shown" — no branch deletion, no tree restore, no assertion. Separately, `cut-pr-branch.sh:171` (`git branch -f "$PR_BRANCH" "$BASE_REF"`) force-moves the target branch before any replay: re-running the cut after hand-fixes on the PR branch, or after it was pushed and reviewed, discards those commits with no warning, and PRCUT-03's promise is false whenever the branch already existed. No requirement checks whether the target branch exists, locally or on the push remote (which wsx can read without the network).
*Fix:* require one exit path that restores the recorded original branch, worktree tree and pre-existing target ref (asserted by a scenario that pre-creates the PR branch and then injects a failure), and refuse to cut over an existing target unless `--force`, printing the commits that would be discarded.

## SUSPECTED

**11. CONF-05's inference and WTREE-04's naming collide, and the owner's repos are already ambiguous.**
CONF-05 (`:43`) falls back to "the only local `workspace/*` or `personal/*` branch", erroring on several. WTREE-04 (`:57`) creates `workspace/<name>` for every non-phase worktree, and `CONTRIBUTING-workflow-b.md:12` recommends `workspace/<handle>-my-feature` too. `WORKSPACE-MODE.md:68` records gsd-core with `personal/workspace` **plus** `personal/workspace-backup` and no manifest, and gsd-pi with `personal/workspace` and no manifest — two candidates before wsx adds any. So the fallback is guaranteed to error in gsd-core on first contact, and after `wsx new foo` in gsd-pi the candidate set includes a *feature* branch; a user who picks it gives `cut` the wrong fork point and `check` the wrong comparison. The mechanism is verified; the harm assumes someone resolves the error by picking a branch instead of setting config.
*Fix:* never infer in a repo that has more than one match — require config written by `wsx init`/`migrate`; put non-phase worktrees in a namespace that cannot collide (or document the collision explicitly and exclude `workspace/<name>` from inference).

**12. GUARD-01's new-ref bound is wrong in exactly the fork layout CONF-04 exists for.**
GUARD-01 (`:81`) bounds a new ref with `--not --remotes=<push-remote>`. In gsd-core the push remote is `origin` (the fork) and the base is `upstream` (`WORKSPACE-MODE.md:68`). `--not --remotes=origin` only excludes commits reachable from the fork's own refs, so if the fork does not carry the integration branch (a fresh fork has no `next`; a stale one is behind), the bound collapses and the range becomes upstream history back to the root. GUARD-03 (`:83`) makes that fail *closed*, so the first push of any cleanly cut PR branch is refused until the user fetches/pushes the integration branch into their fork. The mechanism is certain; whether a given repo's history contains a forbidden path there determines the refusal, and no requirement tests the fork shape at all.
*Fix:* bound with `--not --remotes=<base-remote> --not --remotes=<push-remote>`, and add a harness scenario with base on `upstream`/push on `origin` and no `origin/<integration>` ref.

**13. WTREE-01/03 assume the ROADMAP and the update path that the oracle does not have.**
WTREE-01 (`:54`) checks for a `### Phase N:` heading in "ROADMAP.md" without saying which checkout's copy; the oracle greps the cwd (`scripts/workspace/phase-worktree.sh:53`), which in gsd-pi is a `fix/` branch (`WORKSPACE-MODE.md:69`) and can disagree with the workspace branch the worktree is created from — the authoritative copy is `git show $workspace:.planning/ROADMAP.md`. WTREE-03 (`:56`) offers only fast-forward, and WSYNC-01 (`:48`) forbids syncing from anywhere but the workspace branch, so once a phase branch has one commit there is *no* supported way to bring it up to date with the integration branch mid-phase — re-running `wsx new` refuses (oracle: "not a fast-forward -- the branch has its own commits"), leaving hand-merges the tool never validates. Whether that matters depends on phase length; it does mean the shell scripts' documented workflow has no wsx equivalent.
*Fix:* state the ROADMAP source revision; add `wsx update <name>` (merge the workspace branch into the phase branch, refuse on conflict, report) or drop the fast-forward-only claim.
