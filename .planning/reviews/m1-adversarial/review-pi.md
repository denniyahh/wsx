## CONFIRMED

### 1. The negative control is deleted by the same milestone that depends on it

**Citation:** `.planning/REQUIREMENTS.md:17` "every fixed defect and every deliberate difference has a `fixed:` scenario that passes on Rust and **still fails on the oracle** (the negative control)"; `.planning/REQUIREMENTS.md:81` "**CUT-03**: Python `bin/wsx` is deleted"; `.planning/REQUIREMENTS.md:23` "A differential proptest checks this against the Python parser"; `.planning/research/ARCHITECTURE.md:504-507` "**Differential-only harness** … at cutover the oracle is deleted and every assertion goes with it. A defect present in both implementations passes. **Do this instead:** explicit `Expect` values plus a check that the oracle agrees."

**Problem:** The research already identified this exact failure and prescribed explicit expectations with the oracle as a *secondary* check. The requirements adopted the failing design instead. At CUT-03 the negative control ceases to exist, so the final state of M1 cannot prove any fix was a fix, and CORE-01's differential proptest becomes unrunnable. The suite "keeps passing on Rust alone" (CUT-03) precisely because it stops testing anything the oracle distinguished.

**Why it matters:** Every data-loss fix in M1 (SYNC-02/03/04/05, SAFE-02/03, GUARD-01/03) is validated only by a scenario that is designed to fail on a binary that will be deleted in the same milestone. The suite can be green while a reverted fix still passes, as long as the scenario was also added to the oracle-expected-fail list.

**Fix:** Restate HARN-04: every scenario carries a literal `Expect` (exit code, file contents, status tokens, oracle-independent), and separately an `oracle:` tag; the oracle comparison is a *one-time* recorded artifact (fixture directory of expected oracle outputs, checked in, hashed) so the control survives CUT-03. Add to CUT-03: "the recorded oracle expectations remain in-tree and the suite still runs them." Move CORE-01's differential proptest under the same rule, or re-scope it to golden corpus files.

### 2. "Never read stdin" contradicts a requirement, the contributing rules, four codebase docs and the oracle

**Citation:** `.planning/PROJECT.md:84` "**Non-interactive**: never prompt or read stdin. It runs in git hooks and agent hooks."; `.planning/REQUIREMENTS.md:67` "**GUARD-06**: Agent session hooks … sync the worktree named in the hook's **stdin `cwd`**"; `CONTRIBUTING.md:14-16` "**Never consume stdin in hook paths.** … `pre-push` reads its refs from stdin"; `.planning/codebase/CONVENTIONS.md:77` "Never read stdin anywhere reachable from `wsx hook` (constraint 3)"; `bin/wsx:1023` "Entry point for git hooks. Never reads stdin".

**Problem:** One requirement requires a behaviour that a constraint, a design rule and the oracle's docstring forbid. The requirements never say which hook names may read stdin, on which descriptors, or how a shared-stdin husky path is distinguished from an agent payload. Note `integrations/husky-init.sh:29` already redirects `</dev/null` per-command, which is what makes the git-hook side safe — that mechanism is invisible to the requirements.

**Why it matters:** The obvious implementation ("read stdin in hook mode to get `cwd`") blocks forever when the hook is invoked from a terminal, and consumes the agent's payload before any other hook can see it. The obvious implementation of the constraint (never read stdin) makes GUARD-06 unimplementable. Either reading of the doc set is wrong.

**Fix:** Replace PROJECT.md:84 with: "Never prompts. Reads stdin only for `hook session-start`/`session-end`, only to EOF-bounded JSON on a non-tty, with a hard read timeout; git hooks never read stdin." Add to GIT-02/GUARD-06: "a bounded read that fails open".

### 3. GUARD-02's "pushed range" is unknowable, and GUARD-02/03 never execute in the common repo

**Problem:** GUARD-02 promises a guarantee the research says is unavailable under the stdin constraint, and silently drops the `push origin other-branch` case. Independently, the guard is dead code in any repo without a tracked `.husky/pre-push`, and the only detector the research recommends (PITFALLS.md:158, "`doctor` reports whether `.husky/pre-push` exists") is not in any M1 requirement — "richer `doctor`" is M2 (`PROJECT.md:62`). **Why it matters:** M1's headline guard work (first push, per-commit range) can be fully "done" and still never fire for the author's own repo layout or for any repo missing one file. ### 4. Fail-closed is scoped to "internal error", which is undefined — and the blast radius is every repo on the machine

**Citation:** `.planning/REQUIREMENTS.md:65` "An internal error in the guard blocks the commit or push … (fails closed)"; `integrations/husky-init.sh:28-29` `if [ "${WSX_SKIP:-0}" != "1" ] && [ -x "$HOME/.local/bin/wsx" ]; then "$HOME/.local/bin/wsx" hook "$n" </dev/null || exit 1`; `.planning/codebase/CONCERNS.md:63` "an unexpected exception inside `cmd_guard` also returns 0, so the guard **fails open** on errors (e.g. a manifest parse `Problem` at `:1164-1168`)"; `.planning/REQUIREMENTS.md:56-57` GIT-03 reftable "refused", GIT-04 untrusted repo "refused".

**Problem:** The hook is installed machine-wide for every husky hook in every repo (line 29). "Internal error" is not defined relative to the two *normal* states the guard must handle: (a) this repo is not wsx-configured, (b) configured but the source worktree/branch is missing. Option (a) must allow; option (b) cannot be evaluated. Under a literal fail-closed rule, the reftable refusal (GIT-03), the trust refusal (GIT-04) and a malformed `.wsx.conf` (CONCERNS.md:63) all block every commit in repos where wsx has nothing to guard. Note the guard is also trivially disabled today by unsetting `wsx.sourceBranch` or removing the source worktree (`guard_paths` returns `[]` when not configured) — no requirement closes that.

**Why it matters:** A guard that can block every commit on the machine because an unrelated repo is reftable is a worse failure than the data loss it prevents; and a guard that silently disappears when the source worktree is missing is not a guard. Both are reachable in normal use.

**Fix:** Replace GUARD-04 with an explicit outcome table: "not configured → exit 0 (allow); configured and source worktree missing or manifest unreadable → exit 1 with instructions, unless `WSX_SKIP=1`; unsupported repo (reftable/GIT-04) → exit 0 in hook mode and exit 2 interactively; unexpected panic/IO error in a configured repo → exit 1." Add "the guard is considered configured if either `.wsx.conf` is readable **or** `base.json`/`exclude.wsx-*` exists" so config deletion cannot silently disarm it.

### 5. SAFE-02 reintroduces decision logic into the executor and has no defined outcome for deletes

**Citation:** `.planning/REQUIREMENTS.md:45` "If it changed since planning, the action is **downgraded to a conflict**"; `.planning/REQUIREMENTS.md:31` "**All** sync decisions come from a pure planner"; `CLAUDE.md:23-25` "Sync decisions live **entirely** in `plan()` … Put new decision logic in `plan()`, never in `apply()`"; `.planning/research/PITFALLS.md:76` "This is a precondition check, not a new decision, so it does not break the 'all decisions in `plan()`' rule"; `bin/wsx:397-398` (`lww` emits `delete-local` with no base), `:410-412` (delete-remote/conflict).

**Problem:** "Downgraded to a conflict" *is* a decision and has side effects: writing `<file>.wsx-remote`, choosing which side is "remote", clearing or preserving the base entry. For a planned `delete-local` (source absent — `bin/wsx:397-398`, `:407-408`) there is no source content to put in the marker, so "conflict" is undefined; for a file that vanished or became unreadable between plan and apply, SYNC-02 forbids the delete and SAFE-02 has no fallback. The research's own rationalisation ("not a new decision") is an assertion, not a mechanism, and the requirement text repeats it without the carve-out.

**Why it matters:** This is the exact seam the rewrite is meant to close. Leaving it ambiguous guarantees the executor ends up branching on `policy` and observed state — the anti-pattern CLAUDE.md names — and the race path is the least-tested code in the system.

**Fix:** Split into SAFE-02a ("the executor re-hashes and **aborts** the action with `Outcome::Raced`, writing no conflict marker and no base entry, when the observed hash differs from the planned expectation") and SAFE-02b ("the planner's next run classifies the raced path; conflicting content is only ever created by the planner"). Add a per-kind table: pull/push race → conflict (both sides exist); delete race where the file still exists → skip + report; unreadable → skip + report.

### 6. Crash-after-pull produces a permanent false conflict; "atomically" is not "durably", and no ordering is required

**Citation:** `.planning/REQUIREMENTS.md:49` "A crash or kill at any point during apply leaves no data lost, and the next run **converges correctly**"; `bin/wsx:465-466` (`copy_file(...)` then `base[rel] = digest(dst_path)`), `:483-484` (`if not dry_run: ctx.save_base(base)`); `.planning/REQUIREMENTS.md:26` "`base.json` v2 … written **atomically**"; `.planning/research/PITFALLS.md:320` "`fsync` the file, then `rename` … For `base.json` and backups, also `fsync` the parent directory"; `.planning/research/PITFALLS.md:326` (I3 "backup is durable before the overwrite").

**Problem:** Crash between the copy and `save_base` leaves base = h0 while both live sides are h1, which `plan()` classifies as "changed on both sides" (`bin/wsx:406-412`) — a conflict requiring manual `resolve`, not convergence. Saving base before the data write is worse (base ahead → next run pushes stale local content over the source). `base.json` "atomically" via rename is not crash-atomic on power loss without file+directory fsync, and no requirement states the order of backup → data → base. SAFE-06 will be tested by fault injection written against whatever order the implementer chooses, so it cannot fail.

**Why it matters:** SAFE-06 is the requirement that licenses "every destructive write is backed up"; as written it is satisfied by a plan/apply split that the oracle itself violates.

**Fix:** Add to CORE-04: "base.json is written after the data action it describes, fsynced (file and directory), and upgraded in place only via temp+fsync+rename." Add to SAFE-06: "Recovery rule: if both live sides hash equal, the base adopts that hash without a conflict. Fault injection at every step boundary (before backup, after backup, after rename, before base write) asserts exactly one of: converged, conflict, or skipped — never data loss." State the crash-ordering invariant explicitly in the requirements, not only in ARCHITECTURE.md.

### 7. Backups live in the worktree's private git-dir, so `wsx rm` destroys them

**Citation:** `.planning/REQUIREMENTS.md:46` "Every overwrite or delete, under any policy, backs up the previous content first"; `bin/wsx:144-145` `self.state_dir = self.git_dir / "wsx"`; `bin/wsx:333-338` `dest = ctx.state_dir / "backups" / stamp / label / rel`; `bin/wsx:943-946` `remove = ["worktree", "remove", str(target)] … git(*remove, ...)`.

**Problem:** Backups of *source* content (written by `push`, `resolve --mine`, and under SAFE-03 also `delete-remote`) are stored under the dev worktree's `<git-dir>/wsx/backups/`, and `wsx rm` deletes that git-dir. So the recovery path for the exact operation `rm` performs (push back, then remove) is destroyed by the removal. SAFE-05's pruning makes it worse. No requirement says backups survive worktree removal, and no requirement says a failed backup (ENOSPC, read-only backup dir, EACCES on a subdirectory) aborts the destructive action rather than proceeding.

**Why it matters:** The owner decision "every destructive write backed up" is only true until the next `wsx rm` or disk-full event. The most likely data-loss complaint ("I removed the worktree and the source got clobbered") has no recovery.

**Fix:** Add SAFE-03a: "Backups are written under `<common-dir>/wsx/backups/<worktree-id>/…` so they outlive worktree removal; `wsx rm` never deletes backups (it reports their location)." Add SAFE-03b: "If the backup cannot be written, the action is aborted and reported; the destructive write never proceeds." Add SAFE-05a: retention counts both per-path and total bytes.

### 9. SYNC-07 only protects the local side; a symlinked source path plans a mass deletion

**Citation:** `.planning/REQUIREMENTS.md:37` "Symlinks under managed paths … are never followed, replaced or deleted. They are reported."; `bin/wsx:237-241` `digest()` returns `None` for `path.is_symlink()`; `bin/wsx:397-398` `lww`: `if source_hash is None: … "delete-local"`; `bin/wsx:407-408` `sync`: `if base_hash == local_hash: kind = "pull" if source_hash is not None else "delete-local"`.

**Problem:** The requirement's subject is implicitly the worktree. If the *source* worktree has a symlink at a managed path (e.g. `.claude -> /home/me/dotfiles/claude`, or a leftover link from the pre-migration layout), `digest(source)` is `None`, and every policy plans `delete-local` for every file under it: `pull` mirrors absence, `lww` says "gone upstream", `sync` sees `base == local` and deletes. SYNC-08 only covers interruption *mid-migration*; nothing covers a symlink observed on the source side.

**Why it matters:** One symlink in the personal branch silently deletes every dev copy of a managed tree, which is exactly the Core Value violation. It is also not repairable by the migration path, because `via_symlink()` is only consulted for the local root (`bin/wsx:378`).

**Fix:** Rewrite SYNC-07: "A symlink at any level of a managed path on **either** side is `Special`: wsx never follows, replaces or deletes it and never plans a delete of any file beneath it; the whole subtree is skipped and reported. Only the migration path (SYNC-08) may replace a symlink in a dev worktree, and only when the source side is a real directory." Add a harness case with the source path symlinked, asserting no deletion under all four policies.

### 10. The mass-deletion brake has no threshold, halts pushes too, and its report is discarded

**Citation:** `.planning/REQUIREMENTS.md:47` "If a run would delete more managed files than **a set threshold**, it applies **nothing** without `--force` and reports the count"; `.planning/research/FEATURES.md:70` T8 "more than a threshold of tracked files would be deleted in one run, hold **those deletions**"; `integrations/claude/settings-snippet.json:18` (`… >/dev/null 2>&1; true`).

**Problem:** No value, no config key, no absolute-vs-relative rule, and no requirement that the threshold be discoverable from `status`/`doctor`. "Applies nothing" is stronger than the research proposed: an intentional bulk deletion (the user deletes 30 planning docs, then `git clean -fdX` in a sibling) permanently stops *all* sync in that worktree until a human runs `--force` — including pushes of unrelated local edits. In hooks, the report goes to discarded stderr, so the divergence is silent; and `--force` is not available inside a hook, so an agent turn can never clear it.

**Why it matters:** The brake is the last line of defence for "agent ran `git clean`". As written it converts one bulk-delete risk into unbounded unsynced divergence on every subsequent agent turn, with no visible state. That is a second data-loss mode, slower.

**Fix:** "Brake: if the planner's delete count exceeds `max(10, 25% of tracked files)` (configurable via `wsx.massDeleteThreshold`), those deletes and their base updates are held; all non-delete actions still apply. The held set is persisted, printed by `status` and `doctor`, and blocks `wsx rm`'s push-back until resolved. `--force` (interactive only) applies the held deletes; hooks never force."

### 11. Parity is defined by parsing alone; walk, policy resolution and base-key lifetime are unspecified

**Citation:** `.planning/REQUIREMENTS.md:23` "Every `.wsx.conf` … parses to the same entries and policies" (the only parsing-parity requirement); `bin/wsx:265-268` `if name in IGNORED_BASENAMES or name.endswith(CONFLICT_SUFFIX): continue` / `if full.is_symlink(): continue`; `bin/wsx:276` `best_policy, best_len = "skip", -1`; `bin/wsx:281` `len(entry_parts) > best_len` (first equal-length entry wins); `bin/wsx:365` `candidates |= set(base)` + `:369-371` `if policy == "skip": continue`.

**Problem:** Four observable behaviours are load-bearing for parity and appear in no requirement: (a) the walk silently skips `.git`, `node_modules`, `.DS_Store`, `Thumbs.db` and every `*.wsx-remote` on **both** sides, so a user file with that suffix is invisible to sync but still guard-blocked; (b) default policy for a candidate not covered by the manifest is `skip`; (c) duplicate equal-length entries resolve first-wins in `policy_for` but the guard's `managed_paths` includes *all* non-skip entries (`bin/wsx:600-606`), so sync and guard can disagree about the same manifest; (d) base keys for paths whose manifest entry was removed are never pruned — they stay candidates forever and are skipped. A Rust port can drop any of these and still pass all 48 requirements.

**Why it matters:** "Parity" is the milestone. Defining it as manifest parsing means the oracle comparison cannot detect the differences that matter (files that stop syncing, guard/sync disagreement, stale base growth).

**Fix:** Add CORE-06: "The walk skip set (`.git`, `node_modules`, `.DS_Store`, `Thumbs.db`, `*.wsx-remote`, plus the new `*.wsx-tmp`) is part of the parity contract; each entry has a harness case." Add CORE-07: "Duplicate/degenerate manifest entries are a parse error" (or define last-wins) "and the guard uses the identical policy resolution as the planner." Add CORE-08: "Base entries whose path no longer matches any manifest entry are pruned with a report."

### 12. SAFE-01's only numbers are wrong or absent, and "skip and report" is unobservable

**Citation:** `.planning/REQUIREMENTS.md:44` "Hook runs wait at most **about 2 s** for the lock, then skip and report"; `.planning/research/SUMMARY.md:117` "ARCHITECTURE/FEATURES say about 1-2 s, based on Claude's **1.5 s** SessionEnd budget"; `integrations/claude/settings-snippet.json:20` `"timeout": 30`; `integrations/claude/settings-snippet.json:18` `>/dev/null 2>&1; true`.

**Problem:** "about 2 s" is not falsifiable and already exceeds the 1.5 s budget it is justified by; the repo's own installed integration says 30 s. No requirement bounds *total* hook runtime (lock wait + hashes + copies + git spawns), which is what the timeout actually kills. And "report" is a no-op: the shipped agent-hook commands discard stdout and stderr. A skipped session-end sync — the one hook that saves the user's edits — leaves no trace anywhere.

**Why it matters:** SAFE-01 is the requirement that makes concurrent hook runs safe, but it permits a half-second apply that is then killed by the harness, and it defines the failure report in a channel that is thrown away. Combined with SAFE-06's undefined recovery, killed hooks are the expected steady state for slow repos.

**Fix:** "SAFE-01: git-hook lock wait ≤ 500 ms; agent-hook lock wait ≤ 250 ms; total hook runtime budget ≤ 1 s (agent) / 5 s (git), with the remaining budget computed before starting work. On timeout the run performs no writes and records `last_skipped` in base.json, printed by `status`, `doctor`, and at the top of the next successful run." Add a harness case asserting the recorded state after a forced lock timeout.
